# Configuration agent contract

Read and obey [private workflow reporting](private-reporting.md), the paramount package-wide rule. Pass it with the original assignment and keep requests, decisions, blockers and receipts private.

The already-running main session delegates explicit configuration requests to one fresh native agent. Helpers never launch Codex or Claude Code. If supported native delegation is unavailable, report configuration-agent execution as blocked. Inspection and explanation use a transient configuration-agent assignment with the exact ask and relevant context, without a request ID or durable history. That agent uses the existing read helpers directly. Ordinary workflow reads use those helpers without invoking the configuration skill or delegating.

For saved changes, the main agent starts a request with the exact user ask and the current checkout, repository, upstream and canonical PR where applicable. It passes the returned request ID, original ask, relevant user constraints, invocation-local instructions/options and this contract to a fresh native agent. Assign configuration only: saved dk-workflows settings, preferences and skill selections/options. Skill prompt or runtime edits, plugin installation, other plugins' settings and PR execution are outside this assignment. Selecting a skill does not execute it or authorize PR actions.

The configuration agent returns necessary clarification questions through the main agent, including the earlier ask and proposed replacement when they conflict. The main agent retains the request ID, relays questions and records only necessary answer excerpts with `clarify`. Continue the same native agent where supported. After interruption, call `resume`, reconcile any existing native agent through the host's native tools, and resume the saved request rather than starting a duplicate agent. If the previous native execution cannot be reconciled, report incomplete; a helper cannot manufacture execution evidence or start another session as a workaround. Once the user has settled intent and contradictions, apply without another approval step.

## Admission and application

Use [request commands](configuration-requests.md); deterministic helpers own storage and handoffs. Fetch `show --section ask` to read original wording and clarification excerpts. Read effective values and sources through [configuration](configuration.md), [skill configuration](skill-configuration.md), [PR configuration](pr/configuration.md) and [preferences](preferences.md). Existing values without request records are valid; describe their original intent as unknown. Never infer permission to reset them.

Prepare typed operations to retrieve changed values, stable decision IDs, relevant earlier decisions and an admission fingerprint. Fetch earlier asks or changed values explicitly by request ID when assessing meaning. Assess all candidates across applicable user, upstream, repository and PR scopes, including semantically overlapping settings that have different keys. Helpers detect candidate scopes and exact setting overlap; the native agent checks semantic contradictions and admission against applicable repository instructions.

Return unresolved contradictions to the main agent with both sources and choices to replace, narrow, preserve or cancel. Explicit “replace X with Y” supplies the choice already; do not ask again. Record evidence of the actual choice. A preserved conflicting setting requires removing that proposed change. A narrower repository/PR exception leaves the broader decision active. Replace or narrow only the affected setting decision; preserve other decisions in the earlier request. If narrowing preserves part of a preference, encode that retained scope explicitly in the preference transaction and do not retire a broader decision from a narrower scope. Cancellation remains discoverable.

Submit the assessment against the exact returned fingerprint, listing all reviewed decision references, normalized outcome, resolutions and any outstanding questions. A changed request, relevant configuration, earlier decision, governing resource or instruction requires fresh preparation and assessment. Unchanged `resume` admission is reusable in a fresh session: read compact status, then only the ask, operations or assessment needed to continue. No replay of the conversation or prior admission is needed.

Apply the prepared request once. Helpers commit intent before each store write and verify readback before committing its receipt. After an uncertain result, use the same request ID and `apply` to reconcile values and finish receipts; observed desired values are receipted without another write. Completed siblings are preserved. Unexpected values block recovery. Never blindly rerun an old write or clear request history. Read back the effective settings or affected preference IDs and report their sources and outcome privately.

## Domain decisions

Discover each bundled skill's `config.schema.json` and preserve unrelated settings and invocation controls. New task/finalizer selections are ordered skill-owned invocation lists with explicit parallel groups; a scoped list replaces inheritance and `[]` disables it. Preserve original additional instructions. Do not introduce coordinators, responsibility maps or a declarative condition language. Existing process and hook records remain readable. Resolve external selections through supported native tools; their settings remain owned by that plugin.

For preferences, execute the admission steps in `dk-workflows:dk-preferences` inside this agent; do not recursively delegate. Keep stable preference IDs, exact duplicate reuse, personal/current-repository scope limits, concrete selectors, exclusions, conditions and application modes. Read all applicable preferences, repository layout and instructions including intended new-file ancestors. A helper's structural validation does not establish semantic admission. Include all agreed replacements/removals in one preference proposal. Retain the existing revision boundary and inspect fresh context after changes. Do not convert saved PR rules into preferences automatically.

Preserve exact commit-policy and completion prompts, scope precedence, domain histories and per-PR choices. Verify requested additional personal accounts on their GitHub host and save immutable numeric IDs. Explain user/repository scope before changing automatic posting, fork CI approval, PR approval or merge settings. Enable only requested actions. Posting findings does not authorize approval or merging. Narrower current instructions still govern every workflow action; configuration changes never reset retained CI/retry budgets or review caches.
