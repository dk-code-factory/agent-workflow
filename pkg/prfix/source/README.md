# dk-workflows

Version 5.2.0. Agent-led PR workflows for Codex and Claude Code, with bundled drafting, feedback, publication, cleanup and CI skills. Requires Python 3.11+, Git and authenticated gh for remote PR actions.

Use `dk-workflows:dk-pr-iter` as the universal entry point: it recognizes your accounts and routes your PRs to `dk-workflows:dk-pr-fix` and other authors' PRs to `dk-workflows:dk-pr-review`. Invoke either workflow directly when the intended responsibility is explicit. Fixing runs review/fix cycles followed by [configured finalizers](docs/finalizers.md); the default ending preserves commit cleanup and final CI. Incoming review verifies candidate findings independently before posting; automatic approval and merging each require separate authorization or enabled policy.

"Check out this PR, run dk-pr-iter, then merge it" authorizes that ordered sequence with default settings. Routing and finalization preserve the merge request for your PR or another author's PR. Merge only after current clean review, verification, successful CI and repository requirements pass. Default automatic-merge settings do not veto an explicit request; PR approval remains separately authorized.

Use `dk-workflows:dk-config` when asking to change, inspect or explain saved workflow settings. Ordinary PR routing, review, fixing, splitting and finalization read current settings directly through the documented helpers; they do not invoke the configuration skill. The [configuration invocation exercise](docs/native-config-invocation-exercise.md) checks this boundary against collected request shapes and additional cases. Place custom work before or after review directly in the owning task list. The [cycle-hook API](docs/cycle-hooks.md) remains available for legacy process records. There is no default reviewer. Automatic posting of verified findings is enabled for incoming review; PR approval and merging are disabled by default. Fork workflow approval is enabled by default after complete incoming review, before waiting for CI, independently of PR approval and merge permissions. Narrower instructions, including analysis-only review, override saved policies.

Each skill owns its [explicit defaults and option schema](docs/skill-configuration.md). Configure `tasks` and `finalizers` as ordered lists of fully qualified invocations. Explicit `{"parallel":[...]}` groups run independent skills concurrently and wait for every sibling before proceeding. The owning skill controls repetition and completion. External installed skills are supported. Each scoped list replaces inherited finalizers; `[]` disables them. Final live checks report selected-plan completion separately from skipped cleanup, CI or other readiness evidence.

Configure [commit grouping and message policies](docs/commit-policy.md) through `dk-workflows:dk-config`: save a prompt or select a native policy skill globally or for a repository. For example, “Use dk-config to set my global commit policy to this prompt: squash each PR into one commit and use a short subject-only message.” Policies apply during selected final cleanup and direct `dk-workflows:dk-commit-split` calls, within existing rewrite and publication permissions. The default keeps current cleanup behavior.

Version 4.1 uses [skill-owned configuration](docs/skill-configuration.md) with defaults and option schemas beside each skill. Task lists, reviewers, finalizers, policy providers and drafting use one [invocation format](docs/invocations.md), with additive prompts, validated skill options and native agent model/effort controls. Existing process commands remain compatibility interfaces. Every skill reference uses `plugin:skill`; short names and `/skills/` paths are rejected. Legacy process hooks use list positions and retained phase snapshots instead of user-supplied IDs. See the [compact example](examples/config.json), [complete defaults](examples/config.expanded.json) and migration guidance before replacing older settings. Existing private stores and task-state paths stay in place.

Use `dk-workflows:dk-preferences` for concrete personal or repository instructions scoped to implementation and review. [Preferences](docs/preferences.md) live in a separate private XDG_CONFIG_HOME catalog. Admission settles contradictions before saving; runtime retrieval matches paths and coordinators evaluate conditions. Workflows pass complete scoped records downstream and refresh affected task inputs when applicable preferences change. Existing saved rules stay separate.

The old names are replaced in both host distributions: `dk-pr` → `dk-workflows:dk-pr-iter`; the former maintenance-only `dk-workflows:dk-pr-iter` → `dk-workflows:dk-pr-fix`; the old review coordinator `dk-workflows:dk-pr-review` → `dk-workflows:dk-pr-reviewers-run`; `dk-pr-address-reviews` → `dk-workflows:dk-pr-feedback-address`; `dk-pr-read-comments` → `dk-workflows:dk-pr-feedback-read`; `dk-pr-reply-review` → `dk-workflows:dk-pr-feedback-reply`; `dk-pr-post-review` → `dk-workflows:dk-pr-review-post`; `dk-flaky-tests` → `dk-workflows:dk-ci-flakes`; and `dk-issue-description` → `dk-workflows:dk-issue`. `dk-pr-config` is merged into `dk-workflows:dk-config`; `dk-pr-split-commits` is split into `dk-workflows:dk-pr-split` and `dk-workflows:dk-commit-split`. `dk-pr-commits` is renamed to `dk-workflows:dk-commit-split`. `dk-workflows:dk-pr-review` now denotes the full incoming-review workflow. Update explicitly saved skill selections through `dk-workflows:dk-config`; there are no old-name aliases. Runtime helper folders now match the public skill names: `runtime/dk-pr-feedback-address/` and `runtime/dk-issue/`. Private state paths stay stable, including completion prompts, flake history, task manifests and publication journals.

Install through this plugin’s marketplace or the organization catalog. External reviewers are installed and selected separately; there is no default reviewer. Native agents resolve and invoke skills, which own their procedures and completion reports. [Native reviewer handoffs](docs/native-review.md) retain claim-bound host observations for required independent passes and deeper-look commands; successful execution and a complete report alone cannot establish coverage. Unavailable execution evidence remains incomplete with original results retained. [Architecture](https://github.com/dk-code-factory/dk-architecture) is independent and is never invoked automatically.

Standalone review and iteration share task identities and cached results. Use `dk.py prepare --file REQUEST.json` to define, capture and claim a task group; use `finish` to retain its original result. A new session starts with `resume`, which recaptures saved definitions and returns compact status. Read necessary evidence with `result` and bounded `progress` pages. Hooks and finalizers share this lifecycle. Existing spec/start/record integrations remain compatible; valid results and counters are preserved. Fine-grained fingerprints retain unchanged siblings and content reviews across tree-preserving cleanup. Use `resume --explain` for reuse diagnostics.

[Design](DESIGN.md) and [agent instructions](AGENTS.md) require state to reduce expected total API dollar cost, including the next run in a new session. Retain useful analysis and minimum recovery evidence; avoid duplicate context, derived status and speculative telemetry. Deterministic helpers own bookkeeping and preference-handoff generation. Saved configuration changes use a dedicated native agent with request-bound writes and private Git recovery history; see [configuration requests](docs/configuration-requests.md). Inspection and workflow reads create no request history. Read selected settings together through `config.py show --section ...`; effective settings are not persisted. Common storage primitives preserve legacy paths and locks without resetting caches. Offline tests verify reuse and bounded output; exact API dollar savings require native measurements.

The default fix plan runs commit cleanup and governing-content synchronization before blocking on final-head CI. CI repairs refresh scope, affected reviews and selected cleanup before observation of the resulting final head. Custom finalizer plans control which ending actions run. Observation deadlines, retry counters and review budgets survive interruption. An exhausted five-cycle allowance can receive [explicit user-authorized continuation](docs/task-state.md#retained-budgets) under the same run, preserving its history; a new session alone never resets limits.

Private workflow state lives outside repositories under XDG_STATE_HOME in `dk-workflows/v2`. Atomic claims prevent duplicate launches. Publication journals retain exact intent and require fresh checks; uncertain writes reconcile before another attempt. Direct skill calls use caching only when their caller explicitly manages task state.

Follow the [development instructions](AGENTS.md). Production code must never launch Codex or Claude Code, and skills must never advise doing so, including through referenced runtime guidance or as a fallback. The existing agent session owns skill execution and supported native delegation.

Edit skill prompts under `codex/skills/`, then run `python3 scripts/sync_skills.py` to update the Claude distribution. `python3 scripts/check.py` validates both copies, links, Python syntax and versions. `python3 scripts/test.py` runs all bundled suites offline using real Git and fixture GitHub/native-skill transports. Run controlled native-agent exercises for material recipe changes; offline fixtures do not establish native adherence. `python3 scripts/version.py X.Y.Z` synchronizes release metadata.

Install `pytest`, `pytest-subtests`, `pytest-xdist` and `jsonschema` to run `python3 scripts/test.py --workers 2`, as CI does. JSON Schema is a test dependency; runtime helpers retain their standard-library-only implementation. Recipe scenarios run in parallel after the other workflow tests, keeping Git capture process-count probes separate from concurrent test activity. The other suites retain separate serial processes. Every suite reports its 20 slowest test phases. The default test command remains serial and does not require `pytest-xdist`.

CI checks package validity and PR release versions before installing test dependencies. New PR commits cancel superseded validation runs; main validations remain independent. Releases verify tag identity and main ancestry first, then reuse successful main validation only for the exact tagged commit. Missing, malformed or inaccessible evidence falls back to the complete test suite before publication.

Managed tasks use [completion checklists](docs/task-state.md#completion-checks), with initial evidence acceptance, up to three additional checks by default and completion-only recovery that preserves original analysis.
