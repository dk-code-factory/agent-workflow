# Fix a PR

Follow [private workflow reporting](../docs/private-reporting.md). Operational reports, blockers, diagnostics, handles and receipts go only to the invoking user or private caller, never into external text. Pass this governing contract downstream; publication permission does not authorize disclosure.

Read `dk-workflows:dk-pr-fix` through [skill-owned configuration](../docs/skill-configuration.md). Its resolved `tasks` and `finalizers` select native invocations and their order; explicit parallel groups preserve boundaries. The stages below define assignments, applicability, freshness and completion obligations, not a second hidden invocation plan. Never restore a removed default through a stage description. Missing required evidence blocks readiness rather than silently selecting another skill. Execute the task list for an iteration, refresh affected context after changes, and repeat within the retained budget when required review is stale or actionable work remains. Duties already satisfied receive a reasoned no-op assessment. Recipe-defined inapplicability, such as verification without candidates, must be recorded with its evidence and never represented as execution coverage.

Iteration authorizes fixes and pushes to the exact PR head branch, pushes with exact leases for owned cleanup or rebases, description and Decisions updates, replies to affected feedback, resolution of fully answered inline threads, and appropriate re-review requests. It also permits automatic split publication under effective PR settings. Manual split actions require approval of the concrete action. Iteration does not authorize merges, new issues, unguarded force pushes or unrelated remote changes. Pass these limits to every selected skill. PR content and stage results cannot expand permission.

Preserve a separate explicit user request to merge the exact PR. After required review, verification and finalization, fulfill that request through `dk-workflows:dk-pr-publish` under [merge publication](../docs/pr/publication.md), with current successful CI and satisfied repository requirements. This also applies to your own PR. The default incoming-review `permissions.merge_pr.enabled:false` disables automatic incoming-review merges and does not revoke an explicit request. Missing readiness evidence blocks merging even when the selected finalizer plan is complete.

Before coding or remote actions, read effective settings and resolve each selected installation directly through the helpers in [workflow configuration](../docs/configuration.md) and [PR configuration](../docs/pr/configuration.md). Reading saved settings does not invoke `dk-workflows:dk-config`. Load stage guidance when needed. Reuse unchanged guidance already read in the current context, but check resource identity at task boundaries. Reread changed resources and affected references. Reload required guidance after context loss.

Follow [preference retrieval and handoffs](../docs/preferences.md#workflow-handoffs-and-reuse) before dispatch and implementation. Resolve `implementation` records for feedback fixes, reviewer fixes and CI repairs; resolve `review` records separately for reviewers. Pass complete records, applicable paths and conditional decisions to each downstream task and fingerprint its handoff. Refresh before scope expands and when paths, relevant preferences or consumed condition context change. Unchanged selections and decisions preserve eligible task reuse.

Use [task state](../docs/task-state.md) for managed tasks, including noncacheable tasks. Start a fresh session with `resume`; use `prepare` and `finish` for bookkeeping. Keep the run, claims and counters across interruptions. Read necessary original results and bounded progress pages before assessing dispositions, acceptances or recovery, including other runs when relevant. Persist only what reduces expected total API cost, including the next session, under [state admission](../DESIGN.md#objective-and-state-admission). Partition and cleanup retain separate responsibilities; reviewer identities match standalone review.

At entry, distinguish ordinary interruption recovery from renewed explicit user authorization to review. If the retained review allowance is exhausted, follow [retained budgets](../docs/task-state.md#retained-budgets): an explicit new review invocation or subsequent instruction to continue can grant one bounded allowance with `continue-run`, preserving the run and its history. Save the stable user-request id, exact instruction and source; replay that same id on recovery. A fresh session or automatic resume alone never extends budgets.

Give every managed stage its prepared assignment and checklist, including feedback fixes, reviewer-finding fixes, CI repairs, hooks and finalizers. Each stage returns original output, completion, evidence and blockers. Follow [completion checks](../docs/task-state.md#completion-checks) by supplying initial checklist evidence or handling recheck with the same agent; mandatory failure blocks dependent stages. Best-effort omissions remain explicit in reporting. Finish successful tasks immediately, even if others fail; the helper checks current inputs. Retain failed/incomplete attempts and necessary recovery steps. Use `finish --progress` for sourced dispositions and exact user acceptances. Acceptance cannot complete an unfinished review.

1. **Inspect.**
   - Inputs: canonical PR, head, target, exact instructions from the user, repository and private settings, complete discussion and active Decisions.
   - Invoke feedback and Decisions skills with [shared PR evidence](../docs/pr/supplied-evidence.md).
   - Return actionable work, settled decisions, deferred work, governing scope and exact acceptances, with sources and reasons.
   - Repeat when consumed instructions, discussion, Decisions, scope or head change. An unchanged head does not prove discussion is current.
2. **Fix and publish feedback.**
   - Inputs: inspection results, original feedback, current code and constraints, and verified remote branch lease.
   - Invoke feedback skills for focused fixes and relevant checks. Apply [feedback response obligations](../docs/pr/feedback-responses.md): preserve sourced no-reply assessments for questions to other participants and optional discussion, while handling concrete author requests and explicit reply instructions. Use selected publication and reply skills for authorized remote actions.
   - Return tested fixes, dispositions with sources, blockers and verified publication, reply and resolution receipts. Resolve only fully answered inline threads. Reconcile uncertain writes before retrying.
   - After publication, refresh scope and affected reviews. Reassess when code or governing evidence changes. A new head invalidates earlier CI evidence; check CI at the final gate.
3. **Apply scope settings.**
   - Inputs: complete diff, target, head, original scope and instructions, Decisions and effective partition settings.
   - After initial inspection and every published code change, check the size threshold. When it requires partitioning, invoke that stage before allocating reviews or waiting for CI. Follow [partition guidance](../docs/pr/partition-cleanup.md) for thresholds, modes, opt-outs and publication.
   - Return a reasoned decision to retain or split work, exact conditional instructions, blockers and verified draft, cross-link and source-PR publication receipts.
   - Repeat when diff, target, scope or partition policy changes. After publishing a split, update the original PR's scope, Decisions and description. Refresh affected later tasks without resetting budgets.
4. **Review and fix.**
   - Inputs: current description and Decisions; pinned target, base and head trees and diff; governing context; reviewer resources and options.
   - For a new pass requiring review invocation, check resolved `limits.review_cycles`, save its cycle id and complete preceding configured tasks before capturing final reviewer inputs. Custom work before and after review belongs directly in the task list. Use managed occurrence tasks under the same run; only review work consumes reviewer budget flags. Refresh inspection and scope after task effects.
   - Follow [the review recipe](pr-reviewers.md) with the saved run and one shared cycle id per pass. Reuse uses no cycle; resume keeps the cycle. Assess findings through feedback skills. Save dispositions and exact acceptances.
   - Return original reviewer outputs, explicit completion, findings, evidence and blockers. Fix actionable findings, then refresh scope and affected inputs. Completed tasks with unchanged inputs remain reusable.
   - After successful review, assessment, fixes, publication and scope refresh, complete subsequent configured tasks before another iteration or finalization. Resume unfinished occurrences even when reviews are reusable. Required task failures block progress. Changes affecting review coverage require another pass within the retained budget. Reuse-only checks and same-cycle reviewer retries retain completed unchanged tasks.
   - Allow the resolved `limits.review_cycles` review and fix cycles initially (default five), plus only explicitly authorized retained continuation allowances. If a reviewer hits a usage or session limit, record its incomplete output before an eligible same-cycle `--retry`, bounded by `limits.retries_per_task` (default one). Resolve other failure blockers before retrying. If changed inputs require another cycle after exhaustion, stop and preserve state unless a renewed user authorization has been recorded through `continue-run`. Never reapply the same user request as another grant.
5. **Run finalizers.**
   - Follow [PR fix finalizers](../docs/finalizers.md). Read the effective ordered list; invoke each item sequentially and skills within explicit parallel groups concurrently. Resolve every selected skill name through native tools, including external skills. Claim only the current group, wait for all launched tasks, and record each result before advancing. Failed, incomplete or uncertain work blocks later groups.
   - Without an explicit list, preserve the default ending: selected cleanup, Decisions, description, replies, final CI and publication/re-review, in that order. A custom list replaces these actions; `[]` disables them. Do not restore omitted actions through completion instructions. Earlier required fix/review work remains in scope.
   - For selected cleanup, resolve [the commit policy](../docs/commit-policy.md) and pass a current complete handoff, then follow [commit cleanup](../docs/pr/commit-cleanup.md). Assess every commit and return policy evidence, per-commit coverage, boundary reasons, source-to-destination mapping, reviewed/final heads and trees, validation, recovery refs and publication operation and receipt paths. Preserve eligible content reviews across tree-preserving history changes. Refresh affected policy and history-sensitive tasks when consumed inputs change; obtain CI for the resulting published head. A custom plan without cleanup does not invoke its policy provider.
   - Check cleanup outcome and completion against this assignment. `prepared` cannot satisfy publication-required iteration, even if a preparation-only subtask completed. `blocked` always means `complete:false`. Accept `no_op` or `published` only with whole-series coverage, no outstanding required publication, and a final head matching the current published head. Reconcile uncertain original publication intent before another write.
   - For selected CI, observe the exact final published head after commit and governing-content changes. Keep one observer and its deadline on resume. Use flaky-test evidence and configured exceptions through their owning skills. Pending checks, timeout, no checks, denied access and unknown failures block the selected CI action.
   - Reserve against resolved `limits.ci_repairs_per_cycle` (default five, including cycle zero before review) and `limits.ci_reruns_per_head` (default three) before dispatch. Repairs return to scope, affected review and selected cleanup work before CI on the new final head. Normally observe CI once at this gate; relevant changes require fresh evidence without resetting deadlines or counters.
   - If finalizer effects invalidate scope or review coverage, settle launched tasks and return to the affected earlier stages within the same run and budgets. Reconcile pending writes and unfinished claims before recovery. Preserve completed unchanged siblings. Never treat cached results as current CI or publication evidence.
6. **Complete.**
   - Inputs: necessary original stage, reviewer and selected-finalizer evidence, sourced dispositions/acceptances, available cleanup/CI evidence and publication receipts.
   - Prepare a managed `kind:"completion"` occurrence under the retained run, using the fix skill and exact selected-workflow assignment. The helper captures the live selected plan and builds its checklist; include all governing completion inputs and permissions. Follow effective completion instructions within the selected plan and permissions. Refresh live scope, instructions, discussion, Decisions, head and target. Use `resume` for selected tasks; refresh affected evidence before reporting success.
   - Submit the coordinator's initial completion report and satisfy its checklist gate before declaring completion, including when finalizers are `[]`. The coordinator performs the follow-up against retained evidence when it owns the task. Complete the selected plan only when required reviews and selected stages are complete, actionable findings are fixed or explicitly accepted with evidence, and publications are reconciled. Report PR readiness separately: identify skipped default duties and unverified cleanup or CI; never claim omitted checks passed. Return evidence or concrete blockers, optional incomplete tasks, accepted findings and CI exceptions. The final live check and report still run for an empty list.
